# SDK review — September 5, 2026

Reviewed the SDK's password/signaling paths, request handling, existing reliability and transport coverage, and the website's onboarding, demo, and deployment. SDK baseline: `b7410be`. The source of truth was the working checkout at `../vdoninja` (HEAD `35de379`), with live interoperability checks against both that checkout and `https://vdo.ninja/alpha/`.

## Confirmed and fixed

| Issue | Impact and correction |
| --- | --- |
| Passwords encoded repeatedly | Constructor passwords containing spaces, Unicode, or percent characters changed on room join/reconnect. Preserve internal sanitized values and encode caller input once, matching VDO.Ninja's `lib.js` `sanitizePassword`. |
| Stale stream password hash | Changing the password at room join retained the old stream suffix. Refresh the keyed hash cache before using the new room credentials. |
| Plaintext fallback on encryption failure | SDP and ICE could reach signaling unencrypted despite a configured password. Stop the affected message on encryption failure; retain the existing AES-CBC wire format and explicit password-disabled mode. This concerns signaling metadata, not a change to WebRTC media encryption. |
| RPC response sender unchecked | Another connected peer that knew a request ID could settle the request. Bind replies to the requested UUID. SDK RPC is an application protocol, not VDO.Ninja's remote-control API. |
| RPC error and cleanup paths | Synchronous handler errors escaped; inherited object names could be mistaken for handlers or responses; outstanding requests survived disconnect until timeout. Catch synchronous failures, check owned entries, and cancel requests on disconnect. |
| Peer-supplied HTML in website demo | Messages and sender names were interpolated into `innerHTML`. Render them through `textContent`. Browser reproduction confirmed injected elements before the fix. |
| Demo offered Send too early | The demo enabled Send after signaling/announcement and displayed messages as sent even when `sendData` failed. Enable it after channel readiness and preserve the input on failed sends. |
| Mobile chat clipped | Grid/flex minimum sizing pushed controls beyond a 390px viewport, hidden by page overflow rules. Allow panels and inputs to shrink and wrap long message content. |
| Missing deployment assets | Pages omitted documentation, WHIP/WHEP clients, nested tally samples, and other linked assets. Include them in the published artifact. |
| Misleading onboarding and metadata | Correct the event name and connection timing, provide matching room/host viewer URLs, explain SDK vs iframe use cases and TURN, remove unsupported ratings/stale version/missing share-image references, and distinguish JS/Node from separate Python/Flutter projects. |

The existing metadata-routing test used received `info` where the fixture meant local `localInfo`. Corrected the fixture to exercise local metadata sanitization while preserving the SDK's protection against echoing remote identity.

The runnable workflow example passed real peer RPC, invalid-command rejection, and a byte-for-byte 100,000-byte native file transfer. ## Limits

This is a focused review, not a complete security audit. Live browser checks used installed Chrome and the native tests used `@roamhq/wrtc`; Firefox, Safari, and `node-datachannel` were not exercised in this review. Lossy-network recovery, large-room load, and external WHIP/WHEP ingest remain separate validation tasks. The pre-existing interop notes describe historical file-transfer flakiness; a passing run does not establish its absence under all network conditions.

Changes are local and have not been pushed, published to npm, or deployed. Password fixes can affect SDK-only applications that unknowingly depended on the old double encoding; pass the original password consistently on both ends.
